## 시스템 디자인 면접이란?

시스템 디자인 면접은 **대규모 분산 시스템을 설계하는 능력**을 평가합니다. 정답이 없는 열린 문제로, 요구사항을 분석하고 트레이드오프를 고려하여 합리적인 설계를 도출하는 과정이 중요합니다.

### 평가 요소

| 요소 | 설명 |
|------|------|
| **문제 해결 능력** | 모호한 요구사항을 명확히 정의하는 능력 |
| **확장성 이해** | 트래픽 증가에 대응하는 설계 능력 |
| **트레이드오프 분석** | 여러 선택지의 장단점을 비교하는 능력 |
| **기술적 깊이** | 핵심 컴포넌트에 대한 깊은 이해 |
| **커뮤니케이션** | 생각을 명확히 전달하는 능력 |

## 면접 진행 프레임워크

### Step 1: 요구사항 명확화 (5분)

면접관에게 질문하여 범위를 좁힙니다.

```
기능 요구사항 (Functional Requirements)
├── 핵심 기능은 무엇인가?
├── 사용자는 누구인가?
├── 어떤 플랫폼을 지원하는가? (웹, 모바일, API)
└── 데이터는 어떤 형식인가?

비기능 요구사항 (Non-Functional Requirements)
├── 예상 사용자 수 / DAU는?
├── 읽기 vs 쓰기 비율은?
├── 지연 시간 요구사항은? (실시간 vs 배치)
├── 가용성 요구사항은? (99.9% vs 99.99%)
└── 데이터 일관성 요구사항은?
```

**질문 예시**:
- "일일 활성 사용자(DAU)는 어느 정도로 가정할까요?"
- "읽기와 쓰기 비율은 어떻게 될까요?"
- "글로벌 서비스인가요, 특정 지역 한정인가요?"
- "실시간 응답이 필요한가요?"

### Step 2: 추정 (5분)

트래픽, 저장 용량, 대역폭을 계산합니다.

```
예시: 트위터 같은 SNS

가정:
- DAU: 100M (1억)
- 평균 트윗 수: 2개/일/사용자
- 평균 읽기: 100개/일/사용자

계산:
- 쓰기 QPS: 100M × 2 / 86,400 ≈ 2,300 QPS
- 읽기 QPS: 100M × 100 / 86,400 ≈ 115,000 QPS
- 피크 QPS: 평균 × 3 = 6,900 / 345,000 QPS

저장 용량 (5년):
- 트윗 크기: 평균 300 bytes
- 일일 데이터: 100M × 2 × 300B = 60GB/일
- 5년 데이터: 60GB × 365 × 5 ≈ 110TB
```

**유용한 숫자들**:
```
1일 = 86,400초 ≈ 100,000초 (계산 편의)
1개월 ≈ 2.5M초
1년 ≈ 30M초

1KB = 1,000 bytes
1MB = 1,000 KB
1GB = 1,000 MB
1TB = 1,000 GB

QPS 계산: 요청수 / 86,400
```

## 핵심 개념

### 1. 확장성 (Scalability)

#### 수직 확장 vs 수평 확장

| 구분 | 수직 확장 (Scale Up) | 수평 확장 (Scale Out) |
|------|---------------------|----------------------|
| 방법 | 서버 스펙 증가 | 서버 수 증가 |
| 장점 | 구현 단순 | 무한 확장 가능 |
| 단점 | 물리적 한계, 비용 증가 | 복잡도 증가 |
| 적합 | 소규모, 초기 단계 | 대규모, 성장 단계 |

#### 로드 밸런싱

```
로드 밸런싱 알고리즘
├── Round Robin: 순차 분배
├── Weighted Round Robin: 가중치 기반 분배
├── Least Connections: 연결 수 기반
├── IP Hash: 클라이언트 IP 기반 (세션 유지)
└── Consistent Hashing: 서버 추가/제거 시 재배치 최소화
```

### 2. 가용성 (Availability)

```
가용성 수준           다운타임/년
99%     (two 9s)     3.65일
99.9%   (three 9s)   8.76시간
99.99%  (four 9s)    52.6분
99.999% (five 9s)    5.26분
```

**고가용성 패턴**:
- **Active-Active**: 모든 노드가 트래픽 처리
- **Active-Passive**: 대기 노드가 장애 시 인계
- **데이터 복제**: Primary-Replica 구조

### 3. CAP 정리

분산 시스템에서 **Consistency, Availability, Partition Tolerance** 중 2가지만 동시에 보장 가능

```
        Consistency
           /\
          /  \
         /    \
        / CAP  \
       /________\
Availability  Partition
              Tolerance

CP: 일관성 + 분할 허용성 (응답 지연 허용)
    예: 은행 시스템, 재고 관리

AP: 가용성 + 분할 허용성 (일시적 불일치 허용)
    예: SNS 피드, 캐시 시스템

CA: 일관성 + 가용성 (단일 노드, 분산 X)
    예: 전통적 RDBMS
```

### 4. 일관성 모델

| 모델 | 설명 | 사용 사례 |
|------|------|----------|
| **Strong Consistency** | 모든 읽기는 최신 쓰기 반영 | 금융 거래 |
| **Eventual Consistency** | 시간이 지나면 일관성 수렴 | SNS, 캐시 |
| **Read-Your-Writes** | 자신의 쓰기는 즉시 읽기 가능 | 사용자 프로필 |
| **Causal Consistency** | 인과 관계 있는 작업 순서 보장 | 댓글 시스템 |

### 5. 데이터 파티셔닝

#### 샤딩 전략

```
1. Range 기반
   ├── 장점: 범위 쿼리 효율적
   └── 단점: 핫스팟 발생 가능

   예: user_id 1-1M → Shard 1
       user_id 1M-2M → Shard 2

2. Hash 기반
   ├── 장점: 균등 분산
   └── 단점: 범위 쿼리 어려움

   예: hash(user_id) % shard_count

3. Consistent Hashing
   ├── 장점: 노드 추가/제거 시 재배치 최소화
   └── 단점: 구현 복잡도
```

### 6. 캐싱

#### 캐시 전략

```
Cache-Aside (Lazy Loading)
┌───────────────────────────────────────┐
│ 1. 캐시 확인                          │
│ 2. 캐시 미스 → DB 조회               │
│ 3. 결과를 캐시에 저장                 │
│ 장점: 필요한 데이터만 캐시            │
│ 단점: 첫 요청 느림                    │
└───────────────────────────────────────┘

Write-Through
┌───────────────────────────────────────┐
│ 1. 캐시와 DB 동시 쓰기               │
│ 장점: 캐시 항상 최신                  │
│ 단점: 쓰기 지연                       │
└───────────────────────────────────────┘

Write-Behind (Write-Back)
┌───────────────────────────────────────┐
│ 1. 캐시에 먼저 쓰기                   │
│ 2. 비동기로 DB에 배치 쓰기           │
│ 장점: 쓰기 성능 좋음                  │
│ 단점: 데이터 유실 위험                │
└───────────────────────────────────────┘
```

#### 캐시 무효화

```
TTL 기반: 일정 시간 후 자동 만료
이벤트 기반: 데이터 변경 시 명시적 삭제
버전 기반: 키에 버전 포함하여 갱신
```

### 7. 메시지 큐

```
동기 처리의 문제
┌────────┐     ┌────────┐     ┌────────┐
│ Client │────>│ Server │────>│   DB   │
└────────┘     └────────┘     └────────┘
               전체 대기        전체 대기

비동기 처리 (메시지 큐)
┌────────┐     ┌────────┐     ┌─────────┐     ┌────────┐
│ Client │────>│ Server │────>│  Queue  │────>│ Worker │
└────────┘     └────────┘     └─────────┘     └────────┘
               즉시 응답        비동기 처리
```

**사용 사례**:
- 이메일 발송
- 이미지 처리
- 알림 발송
- 로그 수집

## 문제별 상세 풀이

### 1. URL 단축 서비스

#### 요구사항

```
기능:
- 긴 URL → 짧은 URL 변환
- 짧은 URL → 원본 URL 리다이렉트

비기능:
- 100M URL 생성/월
- 읽기:쓰기 = 10:1
- 7자리 단축 URL
- 10년 보관
```

#### 추정

```
쓰기: 100M / 30일 / 24시간 / 3600초 ≈ 40 QPS
읽기: 400 QPS
피크: 800 QPS (읽기)

저장 용량:
- 10년 URL 수: 100M × 12 × 10 = 12B
- URL당 500 bytes: 12B × 500B = 6TB
```

#### 설계

```
┌──────────────┐
│    Client    │
└──────┬───────┘
       │
       ▼
┌──────────────┐
│ Load Balancer│
└──────┬───────┘
       │
       ▼
┌──────────────┐     ┌──────────────┐
│  API Server  │────>│    Cache     │
└──────┬───────┘     │   (Redis)    │
       │             └──────────────┘
       ▼
┌──────────────┐
│   Database   │
│  (Sharded)   │
└──────────────┘
```

#### 단축 URL 생성

```
방법 1: Base62 인코딩
- 62^7 = 3.5조 조합 가능
- ID를 Base62로 변환

방법 2: 해시 + 충돌 처리
- MD5/SHA → 앞 7자리
- 충돌 시 salt 추가

방법 3: 사전 생성
- 미리 생성된 키 풀에서 할당
```

```python
# Base62 인코딩 예시
ALPHABET = "0123456789ABCDEFGHIJKLMNOPQRSTUVWXYZabcdefghijklmnopqrstuvwxyz"

def encode(num):
    if num == 0:
        return ALPHABET[0]
    result = []
    while num:
        result.append(ALPHABET[num % 62])
        num //= 62
    return ''.join(reversed(result))

# ID 1234567 → "5BAN" (4자리)
```

#### 데이터베이스 스키마

```sql
CREATE TABLE urls (
    id BIGINT PRIMARY KEY,
    short_url VARCHAR(7) UNIQUE NOT NULL,
    original_url TEXT NOT NULL,
    created_at TIMESTAMP DEFAULT NOW(),
    expires_at TIMESTAMP,
    user_id BIGINT
);

CREATE INDEX idx_short_url ON urls(short_url);
```

### 2. 뉴스 피드 시스템

#### 요구사항

```
기능:
- 게시글 작성
- 팔로우/팔로잉
- 홈 타임라인 (팔로우한 사람 게시글)

비기능:
- DAU: 100M
- 평균 팔로잉: 200명
- 평균 게시글: 2개/일
```

#### 팬아웃 전략

```
Push 모델 (Write 시점에 팬아웃)
┌─────────────────────────────────────────────────┐
│ 게시글 작성 시:                                  │
│ 1. 게시글 저장                                   │
│ 2. 팔로워 목록 조회                              │
│ 3. 각 팔로워 타임라인에 게시글 ID 추가           │
│                                                  │
│ 장점: 읽기 빠름                                  │
│ 단점: 팔로워 많으면 쓰기 느림 (핫 유저 문제)     │
└─────────────────────────────────────────────────┘

Pull 모델 (Read 시점에 집계)
┌─────────────────────────────────────────────────┐
│ 타임라인 조회 시:                                │
│ 1. 팔로잉 목록 조회                              │
│ 2. 각 사용자의 최근 게시글 조회                  │
│ 3. 정렬 후 반환                                  │
│                                                  │
│ 장점: 쓰기 빠름                                  │
│ 단점: 읽기 느림                                  │
└─────────────────────────────────────────────────┘

하이브리드 (권장)
┌─────────────────────────────────────────────────┐
│ 일반 유저: Push 모델 (팔로워에게 푸시)           │
│ 핫 유저(연예인 등): Pull 모델 (읽기 시 병합)     │
└─────────────────────────────────────────────────┘
```

#### 아키텍처

```

│ Client │────>│ Post Server│────>│ Post Store  │
└────────┘     └─────┬──────┘     └─────────────┘
                     │
                     ▼
               ┌───────────┐
               │ Fanout    │
               │ Service   │
               └─────┬─────┘
                     │
                     ▼
               ┌───────────┐
               │ Timeline  │ (Redis)
               │ Cache     │
               └───────────┘

└────────┘     └─────┬──────┘     │ Cache       │
                     │            └─────────────┘
                     │
                     ▼ (핫 유저 게시글 병합)
               ┌───────────┐
               │ Post Store│
               └───────────┘
```

### 3. 채팅 시스템

#### 요구사항

```
기능:
- 1:1 채팅
- 그룹 채팅 (최대 100명)
- 온라인 상태 표시
- 읽음 표시

비기능:
- DAU: 50M
- 평균 메시지: 40개/일
```

#### 프로토콜 선택

```
HTTP 폴링
├── 단순하지만 비효율적
└── 실시간성 부족

Long Polling
├── 연결 유지 후 응답
└── 서버 부하 있음

WebSocket ✓
├── 양방향 실시간 통신
├── 연결 유지
└── 채팅에 가장 적합

Server-Sent Events (SSE)
├── 서버→클라이언트 단방향
└── 알림에 적합
```

#### 아키텍처

```
┌──────────────────────────────────────────────────────────────┐
│                        API Gateway                           │
└───────────────────────────────┬──────────────────────────────┘
                                │
        ┌───────────────────────┼───────────────────────┐
        │                       │                       │
        ▼                       ▼                       ▼
┌──────────────┐        ┌──────────────┐        ┌──────────────┐
│   Chat       │        │   Presence   │        │   User       │
```

## 면접 팁

### Do's

1. **질문을 많이 하라**
   - 요구사항 명확화는 가산점
   - "이 부분은 어떻게 가정할까요?"

2. **트레이드오프를 언급하라**
   - "A 방식은 X가 좋지만 Y가 단점입니다"
   - "이 상황에서는 B가 더 적합합니다"

3. **숫자로 뒷받침하라**
   - "하루 1억 요청이면 초당 약 1,200 QPS입니다"
   - "5년 데이터면 약 X TB가 필요합니다"

4. **단계적으로 접근하라**
   - 먼저 단순한 설계 → 점진적으로 확장
   - "일단 단일 서버로 시작하고, 스케일 아웃을 논의하겠습니다"

5. **면접관과 대화하라**
   - 일방적 설명보다 상호작용
   - "이 부분을 더 깊이 다룰까요?"

### Don'ts

1. **바로 설계에 들어가지 마라**
   - 요구사항 확인 없이 시작하면 감점

2. **하나의 해결책만 고집하지 마라**
   - 여러 대안을 제시하고 비교

3. **모든 것을 다루려 하지 마라**
   - 핵심 컴포넌트에 집중

4. **모르는 것을 아는 척하지 마라**
   - "이 부분은 확실하지 않은데, X로 추정합니다"

5. **침묵하지 마라**
   - 생각하는 과정도 말로 표현
