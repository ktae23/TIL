## Phase 1. 웹의 기본 원리 이해

> "코드를 치기 전에, 웹이 어떻게 동작하는지 먼저 이해한다"

### 실생활 비유: 네이버에 접속하면 무슨 일이 벌어질까?

브라우저 주소창에 `www.naver.com`을 입력하고 엔터를 누르는 순간, 보이지 않는 곳에서 이런 일이 벌어집니다.

```
당신의 브라우저                     인터넷                        네이버 서버
    │                              │                              │
    │  ① "naver.com의 IP가 뭐야?"  │                              │
    │ ─────────────────────────▶   │                              │
    │         (DNS 조회)           │                              │
    │                              │                              │
    │  ② "223.130.195.200이야"     │                              │
    │ ◀─────────────────────────   │                              │
    │                              │                              │
    │  ③ "연결해도 될까?" (SYN)      │                              │
    │ ─────────────────────────────────────────────────────────▶  │
    │                         (TCP 3-Way Handshake)               │
    │  ④ "응, 연결하자" (SYN+ACK)   │                              │
    │ ◀─────────────────────────────────────────────────────────  │
    │  ⑤ "확인!" (ACK)             │                              │
    │ ─────────────────────────────────────────────────────────▶  │
    │                              │                              │
    │  ⑥ "메인 페이지 줘" (HTTP GET)│                              │
    │ ─────────────────────────────────────────────────────────▶  │
    │                              │                              │
    │  ⑦ "여기 있어" (HTTP 200 OK + HTML)                          │
    │ ◀─────────────────────────────────────────────────────────  │
    │                              │                              │
    │  ⑧ HTML을 화면에 그리기       │                              │
    │  (브라우저 렌더링)             │                              │
    ▼                              ▼                              ▼
```

### HTTP vs HTTPS — 엽서 vs 봉인 편지

```
  HTTP (엽서)                           HTTPS (봉인 편지)
  ┌─────────────┐                      ┌─────────────┐
  │ 비밀번호:    │                      │ ■■■■■■■■■■  │
  │ mypass123   │  ← 배달원이          │ ■■■■■■■■■■  │  ← 배달원이 봐도
  │             │    볼 수 있음!        │ (암호화됨)    │    무슨 내용인지 모름
  └─────────────┘                      └─────────────┘

  위험: 중간에 누군가                    안전: TLS/SSL 암호화로
  패킷을 가로채면 내용 노출              내용을 보호
```

- **HTTP**: 데이터가 평문(Plain Text)으로 전송 — 도청 가능
- **HTTPS**: TLS(Transport Layer Security)로 암호화 — 로그인, 결제 등 필수

### 브라우저가 HTML을 화면에 그리는 과정

HTML 파일을 받았다고 바로 화면이 뜨는 게 아닙니다. 브라우저 내부에서 **공장 라인** 같은 과정을 거칩니다.

```
  ┌─────────┐    ┌─────────┐    ┌─────────┐
  │  HTML   │    │  CSS    │    │   JS    │
  │  파일   │    │  파일   │    │  파일    │
  └────┬────┘    └────┬────┘    └────┬────┘
       │              │              │
       ▼              ▼              │
  ┌─────────┐   ┌──────────┐        │
  │ DOM 트리 │   │CSSOM 트리│        │
  │ (뼈대)  │   │ (스타일) │        │
  └────┬────┘   └────┬─────┘        │
       │              │              │
       └──────┬───────┘              │
              ▼                      │
       ┌─────────────┐              │
       │  렌더 트리    │ ◀───────────┘  JS가 DOM/CSSOM을
       │ (뼈대+스타일) │                 변경할 수 있음
       └──────┬──────┘
              │
     ┌────────┼────────┐
     ▼        ▼        ▼
  레이아웃   페인트    합성
  (위치/크기  (색칠     (레이어
   계산)     하기)     합치기)
              │
              ▼
        화면 출력!
```

**비유**: 집을 짓는 과정과 같습니다.
| 단계 | 집 짓기 | 브라우저 렌더링 |
|------|---------|----------------|
| 1단계 | 설계도(도면) 그리기 | HTML → DOM 트리 구축 |
| 2단계 | 인테리어 계획 | CSS → CSSOM 트리 |
| 3단계 | 설계도 + 인테리어 합치기 | 렌더 트리 생성 |
| 4단계 | 각 방의 크기·위치 결정 | 레이아웃(Layout) |
| 5단계 | 벽지 붙이고 페인트칠 | 페인트(Paint) |
| 6단계 | 완성된 집 입주 | 합성(Composite) → 화면 출력 |

### `<script>` 태그의 위치가 중요한 이유

```html
<!-- ❌ 나쁜 예: HTML을 다 읽기도 전에 JS가 실행됨 -->
<head>
  <script src="app.js"></script>  ← 여기서 HTML 파싱이 멈춤!
</head>

<!-- ✅ 좋은 예 1: body 맨 아래에 배치 -->
<body>
  <h1>안녕하세요</h1>
  <script src="app.js"></script>  ← HTML을 다 읽은 후 실행
</body>

<!-- ✅ 좋은 예 2: defer 속성 사용 -->
<head>
  <script src="app.js" defer></script>  ← 다운로드는 바로, 실행은 나중에
</head>
```

```
  기본 <script>     : ████████[다운로드+실행]████████  (파싱 중단!)
  <script async>    : ████[다운로드]██[실행]███████     (순서 보장 안 됨)
  <script defer>    : ████[다운로드]█████████[실행]     (파싱 끝난 후 실행)
                      ─────── HTML 파싱 시간 ───────▶
```

### 리플로우 vs 리페인트 — 왜 웹이 버벅일까?

```
  리플로우 (Reflow) — 비용 큼                리페인트 (Repaint) — 비용 작음
  ┌──────────────────────────┐              ┌──────────────────────────┐
  │ 요소의 크기·위치가 변경     │              │ 색상·그림자만 변경         │
  │                          │              │                          │
  │ 예: width, height,       │              │ 예: color, background,   │
  │     margin, padding 변경  │              │     box-shadow 변경       │
  │                          │              │                          │
  │ → 레이아웃부터 다시 계산!   │              │ → 색칠만 다시 하면 됨      │
  └──────────────────────────┘              └──────────────────────────┘

  성능 팁: transform, opacity 사용 → 합성(Composite) 단계만 처리되어 매우 빠름
```

## Phase 2. HTML/CSS와 DOM 이해

> "웹 페이지의 뼈대를 이해하고, 브라우저가 이를 어떻게 다루는지 안다"

### 실생활 비유: 웹 페이지 = 신문

```
  ┌─────────────────────────────────────────────┐
  │  <header> 오늘의 뉴스                         │  ← 신문 이름 (헤더)
  ├─────────────────────────────────────────────┤
  │  <nav> 정치 | 경제 | 사회 | 문화               │  ← 섹션 탭 (네비게이션)
  ├──────────────────────┬──────────────────────┤
  │  <main>              │  <aside>             │
  │  ┌─<article>──────┐  │  광고               │  ← 사이드바
  │  │ 제목: 오늘 날씨   │  │  관련 기사           │
  │  │ 본문: 맑음...    │  │                    │
  │  └────────────────┘  │                    │
  │  ┌─<article>──────┐  │                    │
  │  │ 제목: 주가 동향   │  │                    │
  │  │ 본문: 상승...    │  │                    │
  │  └────────────────┘  │                    │
  ├──────────────────────┴──────────────────────┤
  │  <footer> © 2025 뉴스                        │  ← 하단 정보 (푸터)
  └─────────────────────────────────────────────┘

  이것이 바로 "시맨틱 HTML" — 각 영역에 의미를 부여하는 태그를 사용
```

### 실제 HTML 코드로 보기

```html
<!-- 위 신문 구조를 실제 코드로 작성하면 -->
<!DOCTYPE html>
<html lang="ko">
<head>
  <meta charset="UTF-8">
  <meta name="viewport" content="width=device-width, initial-scale=1.0">
  <title>오늘의 뉴스</title>
  <link rel="stylesheet" href="style.css">
</head>
<body>
  <header>
    <h1>오늘의 뉴스</h1>
  </header>

  <nav>
    <a href="/politics">정치</a>
    <a href="/economy">경제</a>
    <a href="/society">사회</a>
  </nav>

  <main>
    <article>
      <h2>오늘 날씨</h2>
      <p>전국적으로 맑은 날씨가 이어지겠습니다.</p>
    </article>

    <article>
      <h2>주가 동향</h2>
      <p>코스피가 소폭 상승했습니다.</p>
    </article>
  </main>

  <footer>
    <p>© 2025 오늘의 뉴스. All rights reserved.</p>
  </footer>
</body>
</html>
```

### DOM이란? — HTML의 "살아있는 버전"

HTML 파일은 그냥 텍스트입니다. 브라우저가 이걸 읽으면 **트리 구조의 객체**로 변환하는데, 이것이 DOM입니다.

```
  HTML 소스 코드 (텍스트)              DOM 트리 (객체)
  ─────────────────                 ─────────────────

  <html>                            Document
    <body>                          └── html
      <h1>안녕</h1>        ──▶        ├── head
      <p>반가워</p>                    └── body
    </body>                                ├── h1
  </html>                                 │   └── "안녕" (텍스트 노드)
                                          └── p
                                              └── "반가워" (텍스트 노드)
```

> **핵심 차이**: HTML은 "설계도", DOM은 "실제 건물"
> JavaScript로 건물(DOM)을 리모델링할 수 있지만, 설계도(HTML 파일)는 바뀌지 않음

### DOM 조작 예시 — "JavaScript로 건물 리모델링하기"

```javascript
// 요소 찾기 — "이 건물에서 거실 찾아줘"
const title = document.getElementById('main-title');
const buttons = document.querySelectorAll('.btn');

// 내용 바꾸기 — "거실 벽지 바꿔줘"
title.textContent = '새로운 제목';
title.style.color = 'blue';

// 요소 추가하기 — "방 하나 더 만들어줘"
const newItem = document.createElement('li');
newItem.textContent = '새 항목';
document.querySelector('ul').appendChild(newItem);

// 요소 삭제하기 — "이 방 철거해줘"
const oldItem = document.querySelector('.old');
oldItem.remove();
```

### 이벤트 흐름 — 버튼을 클릭하면 어떤 일이?

웹 페이지에서 버튼을 클릭하면, 이벤트가 **3단계**를 거칩니다.

```
  <html>을 클릭 이벤트가 통과하는 경로:

     ① 캡처링 (위→아래)          ② 타깃             ③ 버블링 (아래→위)
     "범인 수색 중..."           "범인 발견!"         "범인 잡았다 보고!"

        document                   document               document
           │ ↓                        │                       ↑ │
        <html>                     <html>                  <html>
           │ ↓                        │                       ↑ │
        <body>                     <body>                  <body>
           │ ↓                        │                       ↑ │
        <div>                      <div>                   <div>
           │ ↓                        │                       ↑ │
        <button> ──────────▶     [button] ◀──클릭!──▶    <button>
                                   여기!
```

```javascript
// 실제 코드 예시
button.addEventListener('click', function(event) {
  // event.stopPropagation()  → 버블링을 여기서 중단 (부모에게 알리지 않음)
  // event.preventDefault()   → 기본 동작 방지 (예: 링크 클릭해도 이동 안 함)
  console.log('버튼이 클릭됨!');
});
```

### CSS 박스 모델 — 모든 HTML 요소는 "상자"

```
  ┌──────────────────────────────────────────────┐
  │                  margin                       │  ← 다른 상자와의 간격
  │   ┌──────────────────────────────────────┐   │
  │   │              border                  │   │  ← 테두리
  │   │   ┌──────────────────────────────┐   │   │
  │   │   │           padding            │   │   │  ← 내용과 테두리 사이 여백
  │   │   │   ┌──────────────────────┐   │   │   │
  │   │   │   │                      │   │   │   │
  │   │   │   │      content         │   │   │   │  ← 실제 내용 (텍스트, 이미지)
  │   │   │   │                      │   │   │   │
  │   │   │   └──────────────────────┘   │   │   │
  │   │   └──────────────────────────────┘   │   │
  │   └──────────────────────────────────────┘   │
  └──────────────────────────────────────────────┘

  택배 상자를 생각하세요:
     content = 물건
     padding = 완충재 (뽁뽁이)
     border  = 상자
     margin  = 상자들 사이 간격
```

### Flexbox vs Grid — 언제 뭘 쓸까?

```
  Flexbox (1차원 — 한 줄 배치)              Grid (2차원 — 격자 배치)
  ─────────────────────────                ─────────────────────────

  가로 방향:                                ┌────┬────┬────┐
  ┌────┬────┬────┬────┐                    │ 1  │ 2  │ 3  │
  │ 1  │ 2  │ 3  │ 4  │                    ├────┼────┼────┤
  └────┴────┴────┴────┘                    │ 4  │ 5  │ 6  │
                                           ├────┼────┼────┤
  세로 방향:                                │ 7  │ 8  │ 9  │
  ┌────┐                                   └────┴────┴────┘
  │ 1  │
  ├────┤                                   사용 예: 상품 목록, 갤러리,
  │ 2  │                                          대시보드 레이아웃
  ├────┤
  │ 3  │
  └────┘

  사용 예: 내비게이션 바, 버튼 그룹, 카드 한 줄 배치
```

### 실습 과제

1. 위 "신문 레이아웃"을 직접 HTML로 작성해보기
2. CSS로 스타일링 (Flexbox로 네비게이션, Grid로 기사 목록)
3. JavaScript로 "기사 추가" 버튼 만들기 (DOM 조작 연습)

## Phase 3. 백엔드 & 서버

> "서버가 요청을 받아 처리하고 응답하는 전체 구조를 이해한다"

### "백엔드"와 "서버" — 같은 말일까?

흔히 혼용하지만 의미가 다릅니다.

```
  ┌─────────────────────────────────────────────────────────────────────┐
  │                                                                     │
  │  "서버" = 물리적/논리적 컴퓨터 (하드웨어 + OS)                         │
  │  ─────                                                              │
  │  요청을 받아들이고 응답을 보내는 컴퓨터 그 자체.                          │
  │  Linux가 설치된 AWS EC2 인스턴스, 회사 전산실의 랙 서버 등.              │
  │                                                                     │
  │                                                                     │
  │  "백엔드" = 서버 위에서 돌아가는 소프트웨어 영역                          │
  │  ─────                                                              │
  │  비즈니스 로직, API, 데이터 처리 등 사용자 눈에 보이지 않는 코드 전체.      │
  │  Spring Boot 앱, DB 쿼리, 인증 처리, 메시지 큐 연동 등.                │
  │                                                                     │
  │                                                                     │
  │  ┌─────── 서버 (하드웨어/인프라) ──────────────────────────────┐      │
  │  │                                                           │      │
  │  │  OS (Linux)                                               │      │
  │  │  ┌──────────────────────────────────────────────────┐     │      │
  │  │  │  WS (Nginx)          ← 정적 파일 제공, 리버스 프록시 │     │      │
  │  │  └────────┬─────────────────────────────────────────┘     │      │
  │  │           │ 동적 요청 전달                                 │      │
  │  │  ┌────────▼─────────────────────────────────────────┐     │      │
  │  │  │  WAS (Tomcat)        ← 애플리케이션 실행 환경       │     │      │
  │  │  │  ┌───────────────────────────────────────────┐   │     │      │
  │  │  │  │  백엔드 코드 (Spring Boot)                 │   │     │      │
  │  │  │  │  - 비즈니스 로직                           │   │     │      │
  │  │  │  │  - REST API                              │   │     │      │
  │  │  │  │  - DB 연동                                │   │     │      │
  │  │  │  └───────────────────────────────────────────┘   │     │      │
  │  │  └──────────────────────────────────────────────────┘     │      │
  │  └───────────────────────────────────────────────────────────┘      │
  └─────────────────────────────────────────────────────────────────────┘

  정리:
  - 서버 = "건물" (컴퓨터, 인프라)
  - 백엔드 = "건물 안에서 일하는 사람들" (소프트웨어, 로직)
  - 서버 없이 백엔드는 돌아갈 수 없고, 백엔드 없이 서버는 빈 건물
```

### WS vs WAS — "경비실과 사무실"

```
  WS (Web Server)                         WAS (Web Application Server)
  ── Nginx, Apache                        ── Tomcat, Jetty, Undertow
  ────────────────                        ────────────────────────────

  역할: 정적 콘텐츠 제공                    역할: 동적 콘텐츠 생성
  - HTML, CSS, JS, 이미지 파일 전달         - 비즈니스 로직 실행
  - 리버스 프록시 (요청 분배)               - DB 조회/저장
  - SSL 종료 (HTTPS 처리)                  - 인증/인가 처리
  - 로드 밸런싱                            - API 응답 생성


  실제 요청 흐름:

  사용자 ──▶ Nginx (WS) ──┬──▶ 정적 파일이면? → 바로 응답 (빠름)
                          │
                          └──▶ 동적 요청이면? → Tomcat (WAS) → Spring Boot
                                                    │
                                                    ▼
                                               비즈니스 로직 처리
                                                    │
                                                    ▼
                                               DB 조회/저장
                                                    │
                                                    ▼
                                               JSON 응답 반환
```

```
  비유: 식당

  ┌────────────────────────────────────────────────────────────┐
  │                                                            │
  │  WS (Nginx) = 안내 데스크                                    │
  │  ──────────────────────                                    │
  │  - "물 주세요" → 직접 줌 (정적 파일)                           │
  │  - "스테이크 주세요" → 주방으로 전달 (동적 요청)                 │
  │  - 손님이 많으면 주방 여러 개에 분배 (로드 밸런싱)               │
  │                                                            │
  │  WAS (Tomcat) = 주방                                        │
  │  ──────────────────────                                    │
  │  - 주문받은 요리를 실제로 만드는 곳 (비즈니스 로직)               │
  │  - 냉장고에서 재료를 꺼냄 (DB 조회)                            │
  │  - 요리 완성 후 서빙 (JSON 응답)                               │
  │                                                            │
  └────────────────────────────────────────────────────────────┘

  왜 분리할까?
  - WS는 정적 파일을 빠르게 처리하는 데 특화
  - WAS는 비즈니스 로직에 집중
  - WAS가 죽어도 WS가 에러 페이지를 보여줄 수 있음
  - WS 뒤에 WAS를 여러 대 두면 트래픽 분산 가능
```

### HTTP 깊게 이해하기

HTTP는 백엔드 개발의 기본 언어입니다. 모든 API 통신이 HTTP 위에서 동작합니다.

#### HTTP 메시지 구조

```
  ──▶ HTTP 요청 (Request)

  ┌─────────────────────────────────────────────────┐
  │  POST /api/users HTTP/1.1          ← 요청 라인   │
  ├─────────────────────────────────────────────────┤
  │  Host: api.example.com             ← 헤더       │
  │  Content-Type: application/json                  │
  │  Authorization: Bearer eyJhbG...                 │
  │  Accept: application/json                        │
  ├─────────────────────────────────────────────────┤
  │                                    ← 빈 줄      │
  │  {                                 ← 본문(Body) │
  │    "name": "철수",                               │
  │    "email": "cs@example.com"                     │
  │  }                                               │
  └─────────────────────────────────────────────────┘


  ◀── HTTP 응답 (Response)

  ┌─────────────────────────────────────────────────┐
  │  HTTP/1.1 201 Created              ← 상태 라인   │
  ├─────────────────────────────────────────────────┤
  │  Content-Type: application/json    ← 헤더       │
  │  Location: /api/users/42                         │
  ├─────────────────────────────────────────────────┤
  │                                    ← 빈 줄      │
  │  {                                 ← 본문(Body) │
  │    "id": 42,                                     │
  │    "name": "철수",                               │
  │    "email": "cs@example.com"                     │
  │  }                                               │
  └─────────────────────────────────────────────────┘
```

#### HTTP 메서드 — "어떤 동작을 할 것인가"

```
  ┌──────────┬────────────────────────┬──────────┬──────────┐
  │ 메서드    │ 의미                    │ 요청 본문 │ 멱등성    │
  ├──────────┼────────────────────────┼──────────┼──────────┤
  │ GET      │ 조회 (데이터 가져오기)    │ 없음     │ 멱등     │
  │ POST     │ 생성 (새 리소스 만들기)   │ 있음     │ 비멱등   │
  │ PUT      │ 전체 수정 (대체)         │ 있음     │ 멱등     │
  │ PATCH    │ 일부 수정               │ 있음     │ 비멱등   │
  │ DELETE   │ 삭제                    │ 없음     │ 멱등     │
  └──────────┴────────────────────────┴──────────┴──────────┘

  멱등(Idempotent)이란?
  같은 요청을 여러 번 보내도 결과가 같은 것.

  GET /users/1  → 항상 같은 사용자 정보 반환 (멱등)
  POST /users   → 보낼 때마다 새 사용자 생성 (비멱등)
  DELETE /users/1 → 첫 번째는 삭제, 두 번째부터는 "이미 없음" (결과 동일 → 멱등)
```

#### HTTP 상태 코드 — "결과가 어떻게 됐는지 알려주는 신호"

```
  ┌─────┬────────────────────────────────────────────────────┐
  │ 코드 │ 의미                                                │
  ├─────┼────────────────────────────────────────────────────┤
  │     │ 2xx: 성공                                           │
  │ 200 │ OK — 요청 성공                                       │
  │ 201 │ Created — 리소스 생성 성공 (POST 응답)                 │
  │ 204 │ No Content — 성공했지만 응답 본문 없음 (DELETE 응답)     │
  ├─────┼────────────────────────────────────────────────────┤
  │     │ 3xx: 리다이렉션                                      │
  │ 301 │ Moved Permanently — 영구 이동 (URL 변경)              │
  │ 302 │ Found — 임시 이동                                    │
  │ 304 │ Not Modified — 캐시 사용 (변경 없음)                   │
  ├─────┼────────────────────────────────────────────────────┤
  │     │ 4xx: 클라이언트 에러 (요청이 잘못됨)                    │
  │ 400 │ Bad Request — 잘못된 요청 (파라미터 오류 등)            │
  │ 401 │ Unauthorized — 인증 필요 (로그인 안 함)                │
  │ 403 │ Forbidden — 권한 없음 (로그인은 했지만 접근 불가)        │
  │ 404 │ Not Found — 리소스 없음                               │
  │ 409 │ Conflict — 충돌 (이미 존재하는 리소스)                  │
  │ 429 │ Too Many Requests — 요청 횟수 초과 (Rate Limiting)     │
  ├─────┼────────────────────────────────────────────────────┤
  │     │ 5xx: 서버 에러 (서버가 잘못됨)                         │
  │ 500 │ Internal Server Error — 서버 내부 오류                 │
  │ 502 │ Bad Gateway — 게이트웨이/프록시 서버 오류               │
  │ 503 │ Service Unavailable — 서비스 일시 중단 (과부하, 점검)   │
  │ 504 │ Gateway Timeout — 게이트웨이 응답 시간 초과             │
  └─────┴────────────────────────────────────────────────────┘
```

#### HTTP 헤더 — "편지의 겉봉투 정보"

```
  자주 쓰는 요청 헤더:
  ┌──────────────────────┬───────────────────────────────────┐
  │ Content-Type         │ 본문의 데이터 형식                  │
  │                      │ application/json, multipart/form  │
  ├──────────────────────┼───────────────────────────────────┤
  │ Authorization        │ 인증 정보 (토큰 등)                 │
  │                      │ Bearer eyJhbGciOiJ...             │
  ├──────────────────────┼───────────────────────────────────┤
  │ Accept               │ 클라이언트가 원하는 응답 형식        │
  │                      │ application/json                  │
  ├──────────────────────┼───────────────────────────────────┤
  │ Cookie               │ 서버가 이전에 설정한 쿠키 전송       │
  └──────────────────────┴───────────────────────────────────┘

  자주 쓰는 응답 헤더:
  ┌──────────────────────┬───────────────────────────────────┐
  │ Set-Cookie           │ 클라이언트에 쿠키 저장 요청          │
  ├──────────────────────┼───────────────────────────────────┤
  │ Cache-Control        │ 캐시 정책 (max-age, no-cache 등)   │
  ├──────────────────────┼───────────────────────────────────┤
  │ Location             │ 리다이렉트 대상 URL (3xx 응답 시)   │
  ├──────────────────────┼───────────────────────────────────┤
  │ Access-Control-*     │ CORS 관련 설정                     │
  └──────────────────────┴───────────────────────────────────┘
```

#### HTTP/1.1 vs HTTP/2 vs HTTP/3

```
  HTTP/1.1                  HTTP/2                    HTTP/3
  ─────────                 ──────                    ──────

  요청 1 ──▶ 응답 1         요청 1 ──▶                요청 1 ──▶
  요청 2 ──▶ 응답 2         요청 2 ──▶  동시에!        요청 2 ──▶  동시에!
  요청 3 ──▶ 응답 3         요청 3 ──▶                요청 3 ──▶
  (순서대로, 느림)           응답 1 ◀──                응답 1 ◀──
                            응답 2 ◀──  병렬 처리      응답 2 ◀──  + UDP 기반
                            응답 3 ◀──                응답 3 ◀──  (더 빠름)

  - HTTP/1.1: 한 번에 하나씩 (Head-of-Line Blocking)
  - HTTP/2: 하나의 TCP 연결에서 여러 요청 병렬 처리 (Multiplexing)
  - HTTP/3: TCP 대신 QUIC(UDP) 사용, 연결 수립이 더 빠름
```

```
  │ POST     │ /users/1/orders      │ 1번 사용자의 새 주문 생성     │
```

## Phase 4. 데이터베이스 & 인프라

> "데이터를 저장하고, 만든 것을 세상에 공개한다"

### 인덱스 — "책의 목차와 같은 원리"

```
  인덱스가 없을 때 (Full Table Scan):

  "김철수 찾아줘"
  ┌────┬─────────┐
  │ 1  │ 박영희   │ ← 아님
  │ 2  │ 이민수   │ ← 아님
  │ 3  │ 정수진   │ ← 아님
  │ .. │ ...     │ ← 계속 찾음...
  │ 999│ 김철수   │ ← 찾았다! (999번째에서)
  └────┴─────────┘
  → 최악의 경우 전체를 다 뒤져야 함


  인덱스가 있을 때 (B-Tree Index):

  "김철수 찾아줘"
  ┌──────────────────┐
  │     [ㄴ, ㅂ]      │  ← "ㄱ"이니까 왼쪽
  └───┬──────────┬───┘
      ↓          ↓
  ┌────────┐ ┌────────┐
  │[ㄱ, ㄴ] │ │[ㅂ, ㅅ] │  ← "ㄱ" 범위
  └───┬────┘ └────────┘
      ↓
  ┌──────────┐
  │ 김철수 →  │ → 999번 행으로 바로 이동!
  └──────────┘
  → 3단계만에 찾음 (로그 시간)

  인덱스가 있으면 검색 시간이 O(N) → O(log N)으로 줄어듦
```

### 트랜잭션 — "은행 송금의 안전장치"

```
  철수가 영희에게 10만원 송금:

  ┌─────────────────────────────────────────────────────────┐
  │  트랜잭션 시작 (BEGIN)                                    │
  │                                                         │
  │  ① 철수 계좌에서 -10만원   [잔액: 100만 → 90만]            │
  │  ② 영희 계좌에 +10만원     [잔액: 50만 → 60만]             │
  │                                                         │
  │  둘 다 성공? → COMMIT (확정!)                              │
  │  하나라도 실패? → ROLLBACK (둘 다 원래대로!)                 │
  └─────────────────────────────────────────────────────────┘

  만약 ①만 성공하고 ②에서 에러가 나면?
  → ROLLBACK → 철수 계좌도 100만원으로 복구!
  → 이것이 ACID의 원자성(Atomicity)

  ACID 속성:
     A(원자성): 전부 성공 or 전부 실패
     C(일관성): 실행 전후 데이터 무결성 유지
     I(격리성): 동시 트랜잭션 간 간섭 방지
     D(지속성): 커밋된 데이터는 영구 저장
```

### 클로저 — "함수가 태어난 환경을 기억한다"

```javascript
// 비유: 카운터 기계를 만드는 공장
function createCounter() {
  let count = 0;           // 이 변수는 공장 안에만 존재

  return {
    increment: () => ++count,  // 공장 밖에서도 count에 접근 가능!
    getCount: () => count,
  };
}

const myCounter = createCounter();
myCounter.increment();  // 1
myCounter.increment();  // 2
myCounter.getCount();   // 2

// 밖에서 직접 count를 건드릴 수는 없음 (캡슐화!)
// console.log(count);  // 에러
```

```
  클로저의 동작 원리:

  createCounter() 호출
  ┌─────────────────────────────────┐
  │  let count = 0                  │  ← 이 환경이 메모리에 유지됨
  │                                 │
  │  return {                       │
  │    increment: () => ++count, ───────▶ count를 "기억"하는 함수
  │    getCount: () => count,    ───────▶ count를 "기억"하는 함수
  │  }                              │
  └─────────────────────────────────┘
          │
          ▼
  함수가 반환된 후에도 count는 사라지지 않음!
  increment()를 호출할 때마다 같은 count를 참조
```

### 비동기 프로그래밍 — "라면 끓이면서 설거지하기"

JavaScript는 **싱글 스레드**(일꾼이 1명)이지만, 비동기 처리로 여러 일을 효율적으로 합니다.

```
  설거지하기          5분            설거지하기          3분
```

### 이벤트 루프 — "어떤 순서로 실행될까?"

```javascript
console.log("1. 시작");                    // ① 즉시 실행

setTimeout(() => {
  console.log("2. setTimeout");            // ④ 마지막 (Task Queue)
}, 0);

Promise.resolve().then(() => {
  console.log("3. Promise");               // ③ 세번째 (Microtask Queue — 우선)
});

console.log("4. 끝");                      // ② 즉시 실행

// 출력 순서: 1. 시작 → 4. 끝 → 3. Promise → 2. setTimeout
```

```
  왜 이 순서일까? — 이벤트 루프의 동작:

  ┌─────────────────────────┐
  │      Call Stack          │  ← 지금 실행 중인 코드
  │  (한 번에 하나만 실행)     │
  └───────────┬─────────────┘
              │ Call Stack이 비면
              │ 아래 순서대로 확인
              ▼
  ┌─────────────────────────┐
  │   Microtask Queue       │  ← Promise.then() 등 (먼저!)
  │   [Promise 콜백]        │
  └───────────┬─────────────┘
              │ Microtask가 비면
              ▼
  ┌─────────────────────────┐
  │   Task Queue            │  ← setTimeout 등 (나중에)
  │   [setTimeout 콜백]     │
  └─────────────────────────┘

  규칙: Call Stack 비움 → Microtask 전부 처리 → Task 하나 처리 → 반복
```

### 콜백 → Promise → async/await — "비동기 코드의 진화"

```javascript
// 1. 콜백 (옛날 방식) — "콜백 지옥"
getUser(userId, function(user) {
  getOrders(user.id, function(orders) {
    getOrderDetail(orders[0].id, function(detail) {
      console.log(detail);  // 점점 깊어지는 들여쓰기
    });
  });
});

// 2. Promise (개선) — 체이닝으로 깔끔해짐
getUser(userId)
  .then(user => getOrders(user.id))
  .then(orders => getOrderDetail(orders[0].id))
  .then(detail => console.log(detail))
  .catch(error => console.error(error));  // 에러 처리 한 곳에서

// 3. async/await (현재 권장) — 동기 코드처럼 읽힘
async function showOrderDetail(userId) {
  try {
    const user = await getUser(userId);           // 결과 나올 때까지 기다림
    const orders = await getOrders(user.id);      // 순서대로 실행
    const detail = await getOrderDetail(orders[0].id);
    console.log(detail);
  } catch (error) {
    console.error(error);                         // try-catch로 에러 처리
  }
}
```

```
  진화 과정 비교:

  콜백          func(a, function(b) {           ← 들여쓰기 지옥
                  func(b, function(c) {
                    func(c, function(d) { ... })
                  })
                })

  Promise       func(a)                         ← 평탄해짐, 하지만 .then 체인
                  .then(b => func(b))
                  .then(c => func(c))

  async/await   const b = await func(a);        ← 마치 동기 코드처럼 읽힘!
                const c = await func(b);
                const d = await func(c);
```

```javascript
// Promise.all — 모두 성공해야 성공 (하나라도 실패하면 전체 실패)
// 비유: 팀 프로젝트 — 팀원 모두 제출해야 완성
const [users, products, orders] = await Promise.all([
  fetch('/api/users'),
  fetch('/api/products'),
  fetch('/api/orders'),
]);

// Promise.race — 가장 빨리 끝난 것의 결과만 사용
// 비유: 달리기 시합 — 1등만 인정
const fastest = await Promise.race([
  fetch('/api/server1'),
  fetch('/api/server2'),
]);

// Promise.allSettled — 성공이든 실패든 모든 결과를 받음
// 비유: 설문조사 — 응답/미응답 모두 집계
const results = await Promise.allSettled([
  fetch('/api/a'),
  fetch('/api/b'),  // 이게 실패해도 a의 결과는 받을 수 있음
]);
```

### 모듈 시스템 — "코드를 파일별로 정리하기"

```
  ┌─ utils.js ─────────────────┐    ┌─ app.js ─────────────────────────┐
  │                             │    │                                  │
  │  // 이 파일에서 만든 기능을    │    │  // 다른 파일의 기능을 가져와 사용   │
  │  // 외부로 공개              │    │                                  │
  │  export function add(a, b) {│◀───│  import { add, multiply }       │
  │    return a + b;            │    │    from './utils.js';            │
  │  }                          │    │                                  │
  │                             │    │  console.log(add(2, 3));  // 5   │
  │  export function multiply(  │    │                                  │
  │    a, b) {                  │    └──────────────────────────────────┘
  │    return a * b;            │
  │  }                          │
  └─────────────────────────────┘

  레고 블록처럼 기능을 모듈로 나누면:
     - 코드를 재사용할 수 있고
     - 파일이 작아져서 관리하기 쉽고
     - 이름 충돌을 방지할 수 있음
```

### TypeScript — "실수를 미리 잡아주는 JavaScript"

```
  JavaScript                              TypeScript
  ──────────                              ──────────

  function add(a, b) {                    function add(a: number, b: number): number {
    return a + b;                           return a + b;
  }                                       }

```

### TypeScript 기본 타입 — "변수에 이름표 붙이기"

```typescript
// 기본 타입 — 변수가 어떤 종류의 값을 담는지 명시
let name: string = "철수";        // 문자열만 가능
let age: number = 25;             // 숫자만 가능
let isStudent: boolean = true;    // true/false만 가능
let hobbies: string[] = ["독서", "코딩"];  // 문자열 배열

// 인터페이스 — "이 객체는 이런 모양이어야 해"
interface User {
  id: number;
  name: string;
  email?: string;     // ?는 선택적 (있어도 되고 없어도 됨)
}

// 이제 User 타입에 맞지 않으면 에러!
const user: User = {
  id: 1,
  name: "철수",
  // email은 선택적이라 없어도 OK
};

const badUser: User = {
  id: "abc",   // 에러! id는 number여야 합니다
  name: 123,   // 에러! name은 string이어야 합니다
};
```

### 제네릭 — "어떤 타입이든 OK, 하지만 일관성은 지킨다"

```typescript
// 비유: 택배 상자 — 뭘 담든 OK, 하지만 꺼낼 때 뭐가 들었는지 아는 상자

// 제네릭 없이: 뭐가 들었는지 모르는 상자
function getFirst(arr: any[]): any {
  return arr[0];  // 반환 타입이 any — 뭔지 모름
}

// 제네릭 사용: 라벨이 붙은 상자
function getFirst<T>(arr: T[]): T {
  return arr[0];  // T 타입이 들어가면 T 타입이 나옴
}

getFirst<number>([1, 2, 3]);      // 반환 타입: number
getFirst<string>(["a", "b"]);     // 반환 타입: string
```

```
  제네릭의 동작 원리:

  getFirst<number>([1, 2, 3])
                │
                ▼
  function getFirst<number>(arr: number[]): number
  → T 자리에 number가 들어감
  → 입력도 number[], 출력도 number — 타입 안전!
```

### SPA vs MPA — "앱 같은 웹 vs 전통적인 웹"

```
  전통적인 웹사이트 (MPA: Multi Page Application)

  [페이지 A 클릭]          [페이지 B 클릭]          [페이지 C 클릭]
       │                       │                       │
       ▼                       ▼                       ▼
  서버에 요청 ──▶           서버에 요청 ──▶           서버에 요청 ──▶
  HTML 전체 수신 ◀──       HTML 전체 수신 ◀──       HTML 전체 수신 ◀──
  화면 깜빡! (새로고침)     화면 깜빡!               화면 깜빡!

  예: 네이버 카페, 관공서 사이트 등


  현대적인 웹 앱 (SPA: Single Page Application)

  [최초 접속]                [페이지 이동]            [페이지 이동]
       │                       │                       │
       ▼                       ▼                       ▼
  서버에 요청 ──▶           JS가 화면 교체           JS가 화면 교체
  HTML + JS 번들 수신 ◀──   (서버 요청 없음!)        (서버 요청 없음!)
  초기 로딩 느림             즉시 전환!               즉시 전환!
  (큰 JS 파일)              (깜빡임 없음)             (깜빡임 없음)

  예: Gmail, 인스타그램 웹, 토스 웹 등
```

### 렌더링 전략 비교 — "어디서 HTML을 만들 것인가?"

```
  ┌─────────────────────────────────────────────────────────────────┐
  │                     어디서 HTML을 만드는가?                       │
  ├─────────────┬───────────────────────────────────────────────────┤
  │             │                                                   │
  │   브라우저   │  CSR (Client-Side Rendering)                      │
  │   에서      │  JS가 브라우저에서 HTML을 만듦                       │
  │             │  장점: 페이지 전환 빠름    단점: 첫 화면 느림, SEO 불리 │
  │             │                                                   │
  ├─────────────┼───────────────────────────────────────────────────┤
  │             │  SSR (Server-Side Rendering)                      │
  │   서버      │  매 요청마다 서버가 HTML을 만들어 보냄                 │
  │   에서      │  장점: SEO 유리, 빠른 첫 화면    단점: 서버 부하       │
  │             │                                                   │
  ├─────────────┼───────────────────────────────────────────────────┤
  │             │  SSG (Static Site Generation)                     │
  │   빌드      │  배포 전에 미리 HTML을 만들어둠                       │
  │   시점에     │  장점: 가장 빠름    단점: 자주 바뀌는 데이터에 부적합   │
  │             │                                                   │
  └─────────────┴───────────────────────────────────────────────────┘

  실생활 비유:
     CSR = 레스토랑에서 직접 요리 (주문 후 시간 걸림, 하지만 맞춤형)
     SSR = 주문하면 주방에서 바로 만들어 줌 (빠르지만 주방이 바쁨)
     SSG = 미리 만들어둔 도시락 (가장 빠르지만 메뉴 변경 어려움)
```

```

  ──────────────────                    ──────────────────

       │                                    │

                                             │
                                             ▼

                                             │
                                             ▼
                                        실제 DOM에서 그 <p>만 수정 (최소 업데이트)
                                        (빠름)

  비유: 벽 전체를 다시 칠하기 vs 긁힌 부분만 터치업
```

### 보안 — "흔한 공격과 방어"

```
  ① XSS (Cross-Site Scripting) — "악성 스크립트 주입"

  공격자가 댓글에 이런 걸 입력:
  ┌──────────────────────────────────────────────────┐
  │ <script>document.cookie를 해커서버로 전송</script> │
  └──────────────────────────────────────────────────┘
  → 다른 사용자가 이 댓글을 보면 스크립트가 실행됨!
  → 방어: 입력값에서 <, >, " 등을 이스케이프 처리


  ② SQL Injection — "SQL 쿼리 조작"

  로그인 폼에 이런 걸 입력:
  ┌────────────────────────────────────────┐
  │ 아이디: admin' OR '1'='1' --           │
  │ 비번: (아무거나)                         │
  └────────────────────────────────────────┘
  → WHERE id='admin' OR '1'='1' -- 가 되어 항상 참!
  → 방어: PreparedStatement (파라미터 바인딩) 사용


  ③ CSRF (Cross-Site Request Forgery) — "사용자 모르게 요청"

  사용자가 은행 사이트에 로그인한 상태에서
  해커가 만든 사이트에 접속하면:
  ┌─────────────────────────────────────────────────────┐
  │ <img src="https://bank.com/transfer?to=hacker&      │
  │           amount=1000000">                           │
  └─────────────────────────────────────────────────────┘
  → 사용자의 쿠키로 송금 요청이 자동 전송됨!
  → 방어: CSRF 토큰, SameSite 쿠키 설정
```
