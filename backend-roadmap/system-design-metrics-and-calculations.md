## 1. 트래픽 관련 지표

### QPS (Queries Per Second)

**정의**: 시스템이 초당 처리하는 쿼리(요청) 수

**계산 공식**:
```
QPS = 일일 요청 수 / 86,400 (하루 초 단위)
Peak QPS = QPS × 2~3 (피크 시간대 배수)
```

**실제 계산 예시**:
```
일일 활성 사용자(DAU): 100만 명
사용자당 일일 평균 요청: 10회
일일 총 요청: 1,000만 회

QPS = 10,000,000 / 86,400 ≈ 116 QPS
Peak QPS = 116 × 3 ≈ 350 QPS
```

### TPS (Transactions Per Second)

**정의**: 초당 처리하는 트랜잭션(쓰기 작업) 수. QPS가 읽기/쓰기 모든 요청을 포함한다면, TPS는 주로 **쓰기 작업**에 집중합니다.

**QPS vs TPS 차이점**:

| 구분 | QPS | TPS |
|------|-----|-----|
| 범위 | 모든 요청 (읽기 + 쓰기) | 트랜잭션 (주로 쓰기) |
| 용도 | API 서버, 캐시 성능 측정 | DB, 결제 시스템 성능 측정 |
| 예시 | 검색 쿼리, 페이지 조회 | 주문 생성, 결제 처리 |

**계산 예시** (이커머스):
```
일일 주문 수: 50만 건
주문당 트랜잭션: 3개 (주문 생성, 재고 차감, 결제)
일일 총 트랜잭션: 150만 건

TPS = 1,500,000 / 86,400 ≈ 17 TPS
Peak TPS = 17 × 5 ≈ 85 TPS (이벤트 시)
```

### DAU/MAU (Daily/Monthly Active Users)

**활용**:
- 트래픽 추정의 시작점
- 시스템 규모 파악

**일반적인 비율**:
```
MAU:DAU 비율
- 소셜 미디어: 50% (MAU 1억이면 DAU 5천만)
- 이커머스: 10~20%
- 유틸리티 앱: 5~10%
```

## 2. 저장 용량 계산

### 기본 데이터 크기

```
문자 (ASCII): 1 byte
문자 (UTF-8 한글): 3 bytes
Integer (32-bit): 4 bytes
Long (64-bit): 8 bytes
UUID: 16 bytes (이진) / 36 bytes (문자열)
Timestamp: 8 bytes
```

### DB 레코드 크기 계산

**예시: 사용자 테이블**
```sql
CREATE TABLE users (
    id          BIGINT,        -- 8 bytes
    username    VARCHAR(50),   -- 50 bytes (최대)
    email       VARCHAR(100),  -- 100 bytes (최대)
    password    CHAR(60),      -- 60 bytes (bcrypt)
    created_at  TIMESTAMP,     -- 8 bytes
    updated_at  TIMESTAMP      -- 8 bytes
);
-- 레코드당 약 230 bytes + 오버헤드(~20%) ≈ 280 bytes
```

**예시: 게시글 테이블**
```sql
CREATE TABLE posts (
    id          BIGINT,        -- 8 bytes
    user_id     BIGINT,        -- 8 bytes
    content     TEXT,          -- 평균 500 bytes 가정
    created_at  TIMESTAMP      -- 8 bytes
);
-- 레코드당 약 524 bytes + 오버헤드 ≈ 630 bytes
```

### 연간 저장 용량 계산

**공식**:
```
연간 저장 용량 = 일일 신규 레코드 수 × 레코드 크기 × 365
```

**실제 계산**:
```
일일 신규 게시글: 100만 개
레코드 크기: 630 bytes

일일 용량 = 1,000,000 × 630 bytes = 630 MB/일
연간 용량 = 630 MB × 365 = 230 GB/년
5년 용량 = 230 GB × 5 = 1.15 TB
```

### 인덱스 크기 계산

**일반적인 규칙**:
```
인덱스 크기 ≈ 데이터 크기의 10~30%
B-Tree 인덱스: 키 크기 × 레코드 수 × 1.5 (오버헤드)
```

**예시**:
```
users 테이블 1억 레코드
email 컬럼 인덱스 (평균 30 bytes)

인덱스 크기 = 30 bytes × 100,000,000 × 1.5 = 4.5 GB
```

## 3. 대역폭 계산

### 기본 공식

```
대역폭 = QPS × 평균 응답 크기
```

### 실제 계산

**API 서버 예시**:
```
QPS: 1,000
평균 JSON 응답: 2 KB

대역폭 = 1,000 × 2 KB = 2 MB/s = 16 Mbps
피크 시: 16 Mbps × 3 = 48 Mbps
```

**이미지 서비스 예시**:
```
QPS: 500 (이미지 요청)
평균 이미지 크기: 200 KB

대역폭 = 500 × 200 KB = 100 MB/s = 800 Mbps
```

## 4. 지연 시간 관련 숫자

시스템 설계 시 반드시 기억해야 할 **지연 시간 수치**:

### 메모리/캐시

| 작업 | 지연 시간 |
|------|----------|
| L1 캐시 참조 | 0.5 ns |
| L2 캐시 참조 | 7 ns |
| 메인 메모리 참조 | 100 ns |
| Redis GET | 0.1~0.5 ms |
| Memcached GET | 0.1~0.5 ms |

### 네트워크/디스크

| 작업 | 지연 시간 |
|------|----------|
| SSD 랜덤 읽기 | 0.1 ms (100 μs) |
| HDD 랜덤 읽기 | 10 ms |
| 같은 데이터센터 왕복 | 0.5 ms |
| 대륙 간 왕복 (미국-유럽) | 100~150 ms |

### 데이터베이스

| 작업 | 지연 시간 |
|------|----------|
| MySQL 단순 SELECT | 1~5 ms |
| MySQL 복잡 JOIN | 10~100 ms |
| PostgreSQL 단순 쿼리 | 1~5 ms |
| DB 커넥션 생성 | 10~50 ms |

## 5. 실전 예제: URL 단축 서비스

### 요구사항
- 월간 신규 URL: 1억 개
- 읽기:쓰기 비율 = 100:1
- URL 보관 기간: 5년

### 트래픽 계산

```
쓰기(생성):
- 월간: 100,000,000
- 일간: 100,000,000 / 30 ≈ 3,333,333
- QPS: 3,333,333 / 86,400 ≈ 40 QPS

읽기(리다이렉트):
- QPS: 40 × 100 = 4,000 QPS
- Peak QPS: 4,000 × 3 = 12,000 QPS
```

### 저장 용량 계산

```
URL 레코드:
- short_url: 7 bytes
- original_url: 평균 100 bytes
- created_at: 8 bytes
- 총: ~120 bytes

5년간 총 레코드: 100,000,000 × 12 × 5 = 60억 개
총 저장 용량: 6,000,000,000 × 120 bytes = 720 GB

인덱스 포함: 720 GB × 1.3 ≈ 940 GB ≈ 1 TB
```

### 대역폭 계산

```
쓰기 대역폭: 40 QPS × 120 bytes = 4.8 KB/s
읽기 대역폭: 4,000 QPS × 500 bytes (리다이렉트 응답) = 2 MB/s
```

## 6. 실전 예제: 트위터 타임라인

### 요구사항
- DAU: 3억 명
- 사용자당 일일 트윗 조회: 평균 100개
- 사용자당 평균 팔로잉: 200명
- 트윗 작성 비율: DAU의 10%

### 트래픽 계산

```
읽기 (타임라인 조회):
- 일일 조회: 300,000,000 × 100 = 300억 회
- QPS: 30,000,000,000 / 86,400 ≈ 347,000 QPS

쓰기 (트윗 작성):
- 일일 트윗: 300,000,000 × 0.1 × 5 (평균 5개/활성유저) = 1.5억 개
- QPS: 150,000,000 / 86,400 ≈ 1,736 QPS
```

### 저장 용량 계산

```
트윗 레코드:
- id: 8 bytes
- user_id: 8 bytes
- content: 280자 × 4 bytes = 1,120 bytes
- created_at: 8 bytes
- 미디어 참조: 100 bytes
- 총: ~1,250 bytes

일일 저장: 150,000,000 × 1,250 bytes = 187.5 GB/일
연간 저장: 187.5 GB × 365 = 68 TB/년
```

### 캐시 크기 계산

```
핫 데이터 캐싱 전략: 최근 7일 트윗
7일 트윗 수: 150,000,000 × 7 = 10.5억 개
캐시 크기: 1,050,000,000 × 1,250 bytes = 1.3 TB

Redis 클러스터: 1.3 TB / 64 GB (노드당) ≈ 21개 노드
```

## 7. 실전 예제: 이커머스 플랫폼

### 요구사항
- MAU: 1,000만 명, DAU: 200만 명
- 일일 평균 상품 조회: 20회/사용자
- 일일 주문 수: 10만 건
- 상품 수: 500만 개
- 주문 보관 기간: 3년

### 트래픽 계산

```
상품 조회 (읽기):
- 일일 조회: 2,000,000 × 20 = 4,000만 회
- QPS: 40,000,000 / 86,400 ≈ 463 QPS
- Peak QPS (점심/저녁 시간): 463 × 4 ≈ 1,850 QPS

주문 처리 (쓰기):
- 일일: 100,000건
- TPS: 100,000 / 86,400 ≈ 1.2 TPS
- Peak TPS (세일 기간): 1.2 × 50 ≈ 60 TPS
```

### 저장 용량 계산

```
상품 테이블:
- id: 8 bytes
- name: 100 bytes
- description: 2,000 bytes
- price: 8 bytes
- category_id: 8 bytes
- stock: 4 bytes
- images (JSON): 500 bytes
- created_at: 8 bytes
- 총: ~2,640 bytes

상품 전체 용량: 5,000,000 × 2,640 bytes = 13.2 GB

주문 테이블:
- id: 8 bytes
- user_id: 8 bytes
- total_amount: 8 bytes
- status: 2 bytes
- shipping_address: 200 bytes
- created_at: 8 bytes
- 총: ~240 bytes

주문상세 테이블 (평균 3개 상품/주문):
- 주문당: 3 × 50 bytes = 150 bytes

3년 주문 용량:
- 주문: 100,000 × 365 × 3 × 240 bytes = 26.3 GB
- 주문상세: 100,000 × 365 × 3 × 150 bytes = 16.4 GB
- 총: ~43 GB
```

### 캐시 전략

```
상품 캐시 (인기 상품 10%):
- 500,000 × 2,640 bytes = 1.3 GB

장바구니 캐시 (활성 사용자):
- 평균 5개 상품, 사용자당 100 bytes
- 200,000 (동시 접속) × 100 bytes = 20 MB

세션 캐시:
- 동시 접속 20만, 세션당 1 KB
- 200,000 × 1 KB = 200 MB

Redis 총 필요량: ~2 GB (단일 인스턴스 가능)
```

### 인프라 산정

```
WAS 서버:
- Peak QPS 1,850, 서버당 처리량 500 QPS 가정
- 필요 서버: 1,850 / 500 = 4대
- 여유 포함: 6대

DB 서버:
- 읽기 복제본 3대 (읽기 분산)
- 마스터 1대 (쓰기)
- 총 4대 (HA 구성 시 8대)
```

## 8. 실전 예제: 실시간 채팅 서비스

### 요구사항
- DAU: 500만 명
- 동시 접속자: 50만 명
- 사용자당 일일 메시지 송신: 평균 50건
- 그룹 채팅방 평균 인원: 5명
- 메시지 보관 기간: 1년

### 트래픽 계산

```
메시지 송신:
- 일일 메시지: 5,000,000 × 50 = 2.5억 건
- QPS: 250,000,000 / 86,400 ≈ 2,894 QPS
- Peak QPS: 2,894 × 3 ≈ 8,682 QPS

메시지 수신 (fan-out):
- 그룹 채팅 비율 50%, 평균 5명
- 1:1 메시지: 1.25억 × 1 = 1.25억 건 수신
- 그룹 메시지: 1.25억 × 5 = 6.25억 건 수신
- 총 수신: 7.5억 건/일
- 수신 QPS: 750,000,000 / 86,400 ≈ 8,680 QPS
```

### WebSocket 연결 관리

```
동시 접속 WebSocket:
- 50만 연결
- 서버당 최대 연결: 10,000 (OS 파일 디스크립터 제한 고려)
- 필요 서버: 500,000 / 10,000 = 50대

메모리 사용량:
- 연결당 메모리: ~10 KB
- 서버당 메모리: 10,000 × 10 KB = 100 MB
- 여유 포함 서버당: 4 GB RAM 권장
```

### 저장 용량 계산

```
메시지 레코드:
- id: 8 bytes
- sender_id: 8 bytes
- room_id: 8 bytes
- content: 평균 200 bytes (최대 1,000자)
- type: 1 byte
- created_at: 8 bytes
- 총: ~235 bytes

연간 저장:
- 일일: 250,000,000 × 235 bytes = 58.75 GB
- 연간: 58.75 GB × 365 = 21.4 TB

인덱스 (room_id + created_at):
- 16 bytes × 250,000,000 × 365 × 1.5 = 2.2 TB
- 총: ~24 TB/년
```

### 메시지 큐 처리량

```
Kafka/RabbitMQ 요구량:
- 메시지 발행: 8,682 msg/s (피크)
- 메시지 소비 (fan-out 후): ~26,000 msg/s

파티션 설계 (Kafka):
- 파티션당 처리량: 5,000 msg/s
- 필요 파티션: 26,000 / 5,000 = 6개
- 여유 포함: 12개 파티션
```

### 읽음 확인 처리

```
읽음 확인 이벤트:
- 메시지 열람 시 발생
- 일일 이벤트: 7.5억 건 (수신과 동일)
- QPS: ~8,680 QPS

배치 처리 최적화:
- 5초 간격 배치 → QPS를 1/5로 감소
- 최적화 후: ~1,736 QPS
```

## 9. 체크리스트 상세 가이드

시스템 디자인 시 각 단계별로 무엇을 확인하고 어떤 결정을 내려야 하는지 상세히 설명합니다.

### Step 1: DAU/MAU 확인

**확인 사항**:
- 현재 사용자 수와 예상 성장률
- 지역별 분포 (글로벌 서비스 여부)
- 사용 패턴 (모바일 vs 웹)

**결정 사항**:
```
DAU < 10만: 단일 서버로 시작 가능
DAU 10만~100만: 로드밸런서 + 다중 서버 필요
DAU 100만~1000만: 캐시 레이어 필수, DB 읽기 복제본
DAU 1000만+: 마이크로서비스, 샤딩, 글로벌 배포 고려
```

**실무 팁**:
- 3년 후 예상 DAU로 설계
- 초기에는 수직 확장(Vertical Scaling)으로 시작, 필요 시 수평 확장

### Step 2: 읽기:쓰기 비율 확인

**서비스별 일반적인 비율**:

| 서비스 유형 | 읽기:쓰기 | 특징 |
|------------|----------|------|
| 뉴스/블로그 | 100:1 | 읽기 최적화 우선 |
| 소셜 미디어 | 10:1 | 피드 캐싱 중요 |
| 이커머스 | 50:1 | 상품 캐싱, 주문은 트랜잭션 보장 |
| 채팅 | 1:1 | 양방향, 실시간 처리 |
| IoT 센서 | 1:100 | 쓰기 최적화, Time-series DB |

**결정 사항**:
```
읽기 중심 (10:1 이상):
- 읽기 복제본 확장
- 캐시 레이어 필수 (Redis, CDN)
- CQRS 패턴 고려

쓰기 중심 (1:10 이하):
- 마스터 DB 성능 중요
- 비동기 처리 (Message Queue)
- 쓰기 샤딩 고려
```

### Step 3: QPS 계산 및 서버 규모 결정

**서버 타입별 처리량 기준**:

| 서버 유형 | 예상 QPS | 비고 |
|----------|---------|------|
| API 서버 (Spring Boot) | 500~2,000 | CPU 바운드 작업 기준 |
| API 서버 (Node.js) | 1,000~5,000 | I/O 바운드 작업 기준 |
| Nginx (리버스 프록시) | 10,000~50,000 | 정적 파일 제외 |
| Redis | 100,000+ | 단순 GET/SET |

**서버 수 계산**:
```
필요 서버 수 = (Peak QPS / 서버당 QPS) × 안전 계수(1.5~2)

예시:
Peak QPS: 10,000
서버당 처리량: 1,000 QPS
안전 계수: 1.5

필요 서버 = (10,000 / 1,000) × 1.5 = 15대
```

### Step 4: 저장 용량 및 DB 선택

**DB 선택 기준**:

| 요구사항 | 추천 DB |
|---------|---------|
| 복잡한 조인, 트랜잭션 | PostgreSQL, MySQL |
| 빠른 읽기, 유연한 스키마 | MongoDB |
| 대용량 쓰기, 시계열 | Cassandra, TimescaleDB |
| 그래프 관계 | Neo4j |
| 검색 | Elasticsearch |

**샤딩 필요 시점**:
```
단일 DB 한계:
- MySQL: ~1TB, 1억 레코드
- PostgreSQL: ~2TB, 2억 레코드
- MongoDB: ~2TB (자동 샤딩 권장)

샤딩 키 선택:
- 균등 분포 가능한 키 (user_id, order_id)
- 핫스팟 방지 (날짜만으로 샤딩 X)
```

### Step 5: 대역폭 및 CDN

**CDN 도입 기준**:
```
정적 파일 용량 > 10 GB
이미지/동영상 QPS > 100
글로벌 사용자 비율 > 20%
```

**비용 추정**:
```
CDN 비용 ≈ $0.02~0.08 / GB (트래픽)
월 100TB 트래픽 = $2,000~8,000

자체 서버 대역폭:
AWS: $0.09/GB (첫 10TB 이후)
GCP: $0.12/GB
```

### Step 6: 캐시 전략

**캐시 레이어 선택**:

| 캐시 유형 | 용도 | TTL |
|----------|------|-----|
| 브라우저 캐시 | 정적 자원 | 1일~1년 |
| CDN 캐시 | 이미지, JS/CSS | 1시간~1일 |
| API 캐시 (Redis) | 응답 데이터 | 1분~1시간 |
| DB 쿼리 캐시 | 자주 조회되는 데이터 | 5분~1시간 |

**캐시 히트율 목표**:
```
일반적인 목표: 80~95%
캐시 히트율 < 80%: 캐시 키 전략 재검토
캐시 히트율 > 95%: 캐시 용량 과다 가능성
```

### Step 7: Peak 트래픽 대비

**이벤트별 트래픽 증가율**:

| 이벤트 | 예상 배수 |
|--------|----------|
| 일반 피크 (점심/저녁) | 2~3배 |
| 마케팅 이벤트 | 5~10배 |
| 대규모 세일 (블랙프라이데이) | 10~50배 |
| 바이럴/뉴스 노출 | 10~100배 |

**대비 전략**:
```
1. Auto Scaling 설정
   - 최소 인스턴스: 평상시 트래픽 처리
   - 최대 인스턴스: 피크의 2배
   - 스케일 아웃 트리거: CPU 70%, QPS 임계치

2. 서킷 브레이커 설정
   - 장애 전파 방지
   - Graceful degradation

3. Rate Limiting
   - 사용자당 요청 제한
   - 과도한 트래픽 차단
```
