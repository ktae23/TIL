## MSA 개념

마이크로서비스 아키텍처(MSA)는 하나의 애플리케이션을 작은 독립적인 서비스들로 분해하는 아키텍처 스타일입니다.

### MSA 특징

```
┌──────────────────────────────────────────────────────────────────┐
│                      MSA 핵심 특징                                │
├──────────────────────────────────────────────────────────────────┤
│                                                                   │
│  1. 서비스별 독립 배포                                           │
│     └── 다른 서비스 영향 없이 개별 배포 가능                     │
│                                                                   │
│  2. 기술 다양성                                                  │
│     └── 서비스마다 최적의 기술 스택 선택 가능                    │
│                                                                   │
│  3. 분산 데이터 관리                                             │
│     └── 서비스별 전용 데이터베이스 (Database per Service)        │
│                                                                   │
│  4. 장애 격리                                                    │
│     └── 한 서비스 장애가 전체에 영향 미치지 않음                 │
│                                                                   │
│  5. 팀 자율성                                                    │
│     └── 서비스 담당 팀이 개발-배포-운영 전담                     │
│                                                                   │
│  6. 확장성                                                       │
│     └── 필요한 서비스만 선택적으로 스케일 아웃                   │
│                                                                   │
└──────────────────────────────────────────────────────────────────┘
```

## MSA vs 모놀리식

### 아키텍처 비교

```
모놀리식 아키텍처:
┌─────────────────────────────────────────────────────────────┐
│                    하나의 애플리케이션                        │
│  ┌───────────┬───────────┬───────────┬───────────┐         │
│  │   User    │   Order   │  Payment  │ Inventory │         │
│  │  Module   │  Module   │  Module   │  Module   │         │
│  └───────────┴───────────┴───────────┴───────────┘         │
│                          │                                   │
│                    ┌─────▼─────┐                            │
│                    │ 단일 DB   │                            │
│                    └───────────┘                            │
└─────────────────────────────────────────────────────────────┘

마이크로서비스 아키텍처:
┌─────────┐  ┌─────────┐  ┌─────────┐  ┌─────────┐
│  User   │  │  Order  │  │ Payment │  │Inventory│
│ Service │  │ Service │  │ Service │  │ Service │
└────┬────┘  └────┬────┘  └────┬────┘  └────┬────┘
     │            │            │            │
┌────▼────┐  ┌────▼────┐  ┌────▼────┐  ┌────▼────┐
│ User DB │  │Order DB │  │Payment  │  │Inventory│
│ (MySQL) │  │(MongoDB)│  │DB(Redis)│  │DB(MySQL)│
└─────────┘  └─────────┘  └─────────┘  └─────────┘
```

### 비교 표

| 구분 | 모놀리식 | MSA |
|------|----------|-----|
| 배포 | 전체 배포 | 서비스별 독립 배포 |
| 확장 | 전체 스케일링 | 선택적 스케일링 |
| 개발 | 단순, 빠른 시작 | 초기 복잡, 인프라 필요 |
| 장애 영향 | 전체 시스템 | 해당 서비스만 |
| 기술 스택 | 단일 기술 | 서비스별 다양 |
| 데이터 일관성 | ACID 트랜잭션 | 최종 일관성 (Eventual) |
| 팀 구조 | 기능별 팀 | 서비스별 팀 (Cross-functional) |
| 테스트 | 단순 | 복잡 (통합 테스트 어려움) |
| 디버깅 | 쉬움 | 어려움 (분산 추적 필요) |

### 언제 MSA를 선택할까?

```
┌──────────────────────────────────────────────────────────────────┐
│                    MSA 도입 적합성 체크리스트                      │
├──────────────────────────────────────────────────────────────────┤
│                                                                   │
│  ✅ MSA가 적합한 경우:                                           │
│     □ 서비스 규모가 크고 복잡함                                   │
│     □ 팀 규모가 큼 (2-Pizza rule: 8명 이상)                      │
│     □ 서비스별 독립적인 확장 필요                                 │
│     □ 빠른 배포 주기 필요                                        │
│     □ 도메인이 명확히 분리됨                                      │
│     □ 충분한 DevOps 역량 보유                                    │
│                                                                   │
│  ❌ 모놀리식이 더 나은 경우:                                      │
│     □ 초기 스타트업 / MVP 개발                                   │
│     □ 작은 팀 (5명 이하)                                         │
│     □ 도메인이 아직 불명확함                                      │
│     □ 단순한 비즈니스 로직                                       │
│     □ 인프라/DevOps 경험 부족                                    │
│                                                                   │
└──────────────────────────────────────────────────────────────────┘
```

## 서비스 분리 기준

### 1. 도메인 주도 설계 (DDD)

```
┌──────────────────────────────────────────────────────────────────┐
│                    Bounded Context 기반 분리                      │
├──────────────────────────────────────────────────────────────────┤
│                                                                   │
│  E-commerce 도메인:                                              │
│                                                                   │
│  ┌─────────────────┐  ┌─────────────────┐  ┌─────────────────┐  │
│  │   주문 Context   │  │   결제 Context   │  │   배송 Context   │  │
│  │                  │  │                  │  │                  │  │
│  │ - Order         │  │ - Payment       │  │ - Delivery       │  │
│  │ - OrderItem     │  │ - PaymentMethod │  │ - Tracking       │  │
│  │ - OrderStatus   │  │ - Transaction   │  │ - Address        │  │
│  └─────────────────┘  └─────────────────┘  └─────────────────┘  │
│            │                   │                   │             │
│            ▼                   ▼                   ▼             │
│       Order Service      Payment Service     Delivery Service    │
│                                                                   │
│  같은 용어도 Context마다 다른 의미:                               │
│  - "고객" in 주문 = 주문자 정보                                   │
│  - "고객" in 결제 = 결제 수단 소유자                              │
│  - "고객" in 배송 = 수령인 정보                                   │
│                                                                   │
└──────────────────────────────────────────────────────────────────┘
```

### 2. 비즈니스 역량 (Business Capability)

```java
// 비즈니스 역량별 서비스 분리 예시

/*
 * 온라인 쇼핑몰 비즈니스 역량:
 *
 * 1. 상품 관리 (Product Management)

 *    - 상품 등록, 수정, 삭제

 * 2. 주문 관리 (Order Management)
 *    → Order Service

 *
 * 3. 재고 관리 (Inventory Management)
 *    → Inventory Service
 *    - 재고 조회, 차감
 *    - 입출고 관리
 *
 * 4. 결제 처리 (Payment Processing)
 *    → Payment Service
 *    - 결제 요청, 승인
 *    - 환불 처리
 *
 * 5. 배송 관리 (Shipping Management)
 *    → Shipping Service
 *    - 배송 추적
 *    - 배송 상태 관리
 *
 * 6. 고객 관리 (Customer Management)
 *    → User Service
 *    - 회원가입, 로그인
 *    - 프로필 관리
 */
```

### 3. 변경 빈도와 확장성

```
┌──────────────────────────────────────────────────────────────────┐
│                  변경 빈도 기반 분리                              │
├──────────────────────────────────────────────────────────────────┤
│                                                                   │
│  높은 변경 빈도:                                                  │
│  ┌─────────────────┐                                             │
│  │  Promotion      │ ← 프로모션, 할인 정책 자주 변경              │
│  │  Service        │   → 독립 서비스로 분리                      │
│  └─────────────────┘                                             │
│                                                                   │
│  낮은 변경 빈도:                                                  │
│  ┌─────────────────┐                                             │
│  │  Core User      │ ← 핵심 사용자 정보는 안정적                 │
│  │  Service        │   → 신중하게 변경, 잘 분리                  │
│  └─────────────────┘                                             │
│                                                                   │
│  높은 트래픽/확장 필요:                                           │
│  ┌─────────────────┐                                             │
│  │  Search         │ ← 트래픽 집중, 독립 확장 필요               │
│  │  Service        │   → Elasticsearch 별도 클러스터             │
│  └─────────────────┘                                             │
│                                                                   │
└──────────────────────────────────────────────────────────────────┘
```

```

├──────────────────────────────────────────────────────────────────┤
│                                                                   │

│  - 여러 Bounded Context 혼재                                     │
│  - 배포 시 다른 기능 영향                                        │
│  - 하나의 변경에 여러 팀 조율 필요                               │
│                                                                   │
```

```java
  instance:

    }
```

## 도입 시 고려사항

### 도전 과제

```
┌──────────────────────────────────────────────────────────────────┐
│                    MSA 도입 시 도전 과제                          │
├──────────────────────────────────────────────────────────────────┤
│                                                                   │
│  1. 분산 트랜잭션                                                │
│     - ACID → 최종 일관성 (Eventual Consistency)                  │
│     - Saga 패턴, 보상 트랜잭션 필요                              │
│                                                                   │
│  2. 서비스 간 통신                                               │
│     - 네트워크 지연, 장애 대응                                    │
│     - Circuit Breaker, Retry 패턴                                │
│                                                                   │
│  3. 데이터 일관성                                                │
│     - 분산된 데이터 동기화                                       │
│     - 이벤트 기반 동기화                                         │
│                                                                   │
│  4. 테스트 복잡도                                                │
│     - 서비스 간 통합 테스트 어려움                               │
│     - 계약 테스트 (Contract Test) 필요                           │
│                                                                   │
│  5. 운영 복잡도                                                  │
│     - 다수의 서비스 모니터링                                     │
│     - 분산 로깅, 추적 시스템 필요                                │
│                                                                   │
│  6. 조직 문화                                                    │
│     - DevOps 문화 필요                                           │
│     - 서비스 오너십                                              │
│                                                                   │
└──────────────────────────────────────────────────────────────────┘
```

### 점진적 전환 전략

```

│                  모놀리식 → MSA 전환 전략                         │

│  ┌─────────────────────────────────────────────────────────────┐ │
│  │  기존 모놀리식 ←─ Facade ←─ 신규 요청                        │ │
│  │       ↓                         ↓                            │ │
│  │  레거시 기능              새 마이크로서비스                   │ │
│  │                                                              │ │
│  │  점진적으로 기능을 마이크로서비스로 이전                      │ │
│  └─────────────────────────────────────────────────────────────┘ │
│                                                                   │
│  2단계: 분리 우선순위                                            │
│  - 변경 빈도 높은 모듈                                           │
│  - 확장 필요한 모듈                                              │
│  - 도메인 경계 명확한 모듈                                       │
│                                                                   │
│  3단계: 데이터 분리                                              │
│  - 처음엔 공유 DB → 서비스별 스키마 → 별도 DB                   │
│  - 동기화 메커니즘 구축                                          │
│                                                                   │
└──────────────────────────────────────────────────────────────────┘
```

## 핵심 정리

### MSA 도입 체크리스트

| 항목 | 확인 |
|------|------|
| 도메인 분석 완료 (Bounded Context 정의) | □ |
| 팀 구조 재편 준비 | □ |
| CI/CD 파이프라인 구축 | □ |
| 컨테이너 오케스트레이션 (K8s 등) | □ |
| 서비스 메시/API 게이트웨이 | □ |
| 분산 로깅/추적 시스템 | □ |
| 모니터링/알림 시스템 | □ |
| 장애 대응 전략 (Circuit Breaker 등) | □ |

### 서비스 분리 원칙

```
1. 단일 책임 원칙 (SRP)
   - 하나의 서비스는 하나의 비즈니스 역량

2. 높은 응집도, 낮은 결합도
   - 서비스 내부는 밀접, 서비스 간은 느슨한 연결

3. 독립 배포 가능
   - 다른 서비스 변경 없이 배포 가능

4. 데이터 소유권
   - 각 서비스가 자신의 데이터 소유

5. API 우선 설계
   - 계약(Contract) 먼저 정의
```

### 면접 대비 핵심 질문

1. **Q: MSA의 장단점을 설명해주세요**
   - A: 장점은 독립 배포, 기술 다양성, 확장성, 장애 격리. 단점은 분산 시스템 복잡도, 네트워크 오버헤드, 데이터 일관성 관리 어려움

2. **Q: 서비스 분리 기준은 무엇인가요?**
   - A: DDD의 Bounded Context, 비즈니스 역량, 변경 빈도, 확장 필요성. 하나의 팀이 관리 가능하고 2~3주 내 재작성 가능한 크기가 적절

3. **Q: 모놀리식에서 MSA로 전환하는 전략은?**
   - A: Strangler Fig 패턴으로 점진적 전환. 변경 빈도 높은 모듈부터 분리. 공유 DB에서 시작해 점진적으로 데이터 분리
