# 배포 전략 개요와 비교

배포 전략(Deployment Strategy)은 새로운 버전의 소프트웨어를 프로덕션 환경에 릴리스하는 방법을 정의한다. 각 전략은 다운타임, 리스크, 비용, 롤백 용이성 간의 트레이드오프를 가지며, 서비스 특성에 맞는 전략을 선택하는 것이 핵심이다.

## 1. 핵심 개념 (What)

### 배포 전략의 분류

```
배포 전략
├── Recreate (재생성)
│   └── 기존 전체 중단 → 새 버전 배포
├── Rolling Update (점진적 교체)
│   └── 인스턴스를 하나씩 교체
├── Blue-Green (무중단 전환)
│   └── 두 개의 동일한 환경 간 트래픽 전환
├── Canary (카나리)
│   └── 소수 트래픽으로 새 버전 검증 후 확대
├── A/B Testing
│   └── 사용자 세그먼트별 다른 버전 제공
└── Shadow (미러링)
    └── 프로덕션 트래픽을 복제하여 새 버전에서 테스트
```

## 2. 왜 알아야 하는가 (Why)

### 잘못된 배포의 비용

- **다운타임 비용**: 주요 서비스 1분 다운타임 = 수백만 원 이상의 매출 손실
- **사용자 경험**: 배포 중 서비스 장애는 사용자 이탈로 직결
- **신뢰도**: 잦은 배포 장애는 팀의 배포 자신감을 하락시킴

### 배포 전략은 비즈니스 결정이다

기술적 관점뿐 아니라 비즈니스 요구사항에 따라 전략이 달라진다:

| 비즈니스 요구 | 적합한 전략 |
|-------------|-----------|
| 무중단 서비스 필수 | Blue-Green, Canary, Rolling |
| 비용 최소화 | Rolling Update |
| 리스크 최소화 | Canary, Shadow |
| 빠른 롤백 | Blue-Green |
| 사용자별 기능 테스트 | A/B Testing |

## 3. 내부 구현 분석 (How)

### 1. Recreate (재생성) 배포

```
시간 →
┌────────────┐
│  v1 (구버전) │  ← 전체 중단
└────────────┘
              ┌────────────┐
   다운타임    │  v2 (신버전) │  ← 전체 시작
              └────────────┘
```

**동작 방식:**
1. 기존 버전의 모든 인스턴스를 중단
2. 새 버전의 인스턴스를 시작
3. 헬스 체크 후 서비스 시작

**특징:**
- 가장 단순한 배포 방식
- **다운타임 발생** (중단 ~ 시작 사이)
- 리소스 사용이 가장 적음 (동시에 두 버전 불필요)
- 개발/테스트 환경에 적합

### 2. Rolling Update (점진적 교체)

```
시간 →
Instance 1: [===v1===]→[===v2===]→
Instance 2: [=====v1=====]→[===v2===]→
Instance 3: [========v1========]→[===v2===]→
Instance 4: [===========v1===========]→[===v2===]→
```

**동작 방식:**
1. 한 번에 일정 수의 인스턴스만 교체
2. 새 인스턴스가 Ready 상태가 되면 다음 인스턴스 교체
3. 모든 인스턴스가 교체될 때까지 반복

**특징:**
- 무중단 배포 가능
- 배포 중 v1, v2가 동시에 서비스 (버전 호환성 필수)
- Kubernetes의 기본 배포 전략
- 롤백이 상대적으로 느림

### 3. Blue-Green 배포

```
        Load Balancer
             │
     ┌───────┴───────┐
     ↓               ↓
┌─────────┐    ┌─────────┐
│  Blue   │    │  Green  │
│  (v1)   │    │  (v2)   │
│ Active  │    │ Standby │
└─────────┘    └─────────┘

배포 후 트래픽 전환:

        Load Balancer
             │
     ┌───────┴───────┐
     ↓               ↓
┌─────────┐    ┌─────────┐
│  Blue   │    │  Green  │
│  (v1)   │    │  (v2)   │
│ Standby │    │ Active  │
└─────────┘    └─────────┘
```

**동작 방식:**
1. Blue(현재 버전)와 Green(새 버전) 두 환경 준비
2. Green에 새 버전 배포 및 검증
3. 로드 밸런서의 트래픽을 Blue → Green으로 전환
4. 문제 시 즉시 Blue로 롤백

**특징:**
- 즉각적인 롤백 가능 (트래픽 스위치만 변경)
- 배포 전 충분한 테스트 가능
- **인프라 비용이 2배** (두 환경 동시 운영)
- 데이터베이스 마이그레이션 처리가 복잡

### 4. Canary 배포

```
시간 →

Phase 1: 5% 트래픽
┌────────────────────────────────────────┐  ┌──┐
│           v1 (95%)                      │  │v2│ 5%
└────────────────────────────────────────┘  └──┘

Phase 2: 25% 트래픽 (메트릭 정상 시)
┌─────────────────────────────┐  ┌────────────┐
│        v1 (75%)              │  │  v2 (25%)  │
└─────────────────────────────┘  └────────────┘

Phase 3: 75% 트래픽 (메트릭 정상 시)
┌──────────┐  ┌────────────────────────────────┐
│ v1 (25%) │  │         v2 (75%)                │
└──────────┘  └────────────────────────────────┘

Phase 4: 100% 완료
┌────────────────────────────────────────────────┐
│                 v2 (100%)                       │
└────────────────────────────────────────────────┘
```

**동작 방식:**
1. 소수(1~5%)의 트래픽을 새 버전으로 라우팅
2. 에러율, 응답 시간 등 메트릭을 모니터링
3. 문제가 없으면 트래픽 비율을 점진적으로 증가
4. 최종적으로 100% 트래픽을 새 버전으로 전환
5. 문제 발생 시 즉시 트래픽을 기존 버전으로 복원

**특징:**
- 리스크 최소화 (소수 사용자에게만 영향)
- 실제 프로덕션 트래픽으로 검증
- 메트릭 기반 자동 판단 가능
- 구현 복잡도가 높음 (트래픽 분배, 모니터링)

### 5. A/B Testing 배포

```
사용자 세그먼트 기반 라우팅:

iOS 사용자    → v1 (기존 UI)
Android 사용자 → v2 (새 UI)
또는
Region A     → v1
Region B     → v2
```

**특징:**
- 배포 전략이라기보다 비즈니스 실험 기법
- 사용자 세그먼트별 다른 경험 제공
- 데이터 기반 의사결정
- Feature Flag와 결합하여 사용

### 6. Shadow (Traffic Mirroring)

```
실제 트래픽
    │
    ├──→ v1 (프로덕션) → 실제 응답 반환
    │
    └──→ v2 (Shadow)  → 응답 버림 (결과만 비교)
```

**특징:**
- 실제 트래픽으로 새 버전을 테스트하되 사용자에게 영향 없음
- 성능과 정확성을 프로덕션 환경에서 검증
- 부작용(DB 쓰기, 외부 API 호출) 처리에 주의 필요

## 4. 실전 예제

### 예제 1: 전략별 Kubernetes 설정 비교

```yaml
# Recreate
apiVersion: apps/v1
kind: Deployment
metadata:
  name: my-app
spec:
  replicas: 3
  strategy:
    type: Recreate          # 전체 중단 후 재생성
---
# Rolling Update
apiVersion: apps/v1
kind: Deployment
metadata:
  name: my-app
spec:
  replicas: 3
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxSurge: 1           # 목표 수 대비 최대 1개 추가 가능
      maxUnavailable: 0     # 최소 3개 항상 유지 (무중단)
```

### 예제 2: 전략 선택 의사결정 흐름

```
서비스에 다운타임이 허용되는가?
├── Yes → Recreate (가장 간단)
└── No  → 무중단 배포 필요
          │
          인프라 비용을 2배로 감당할 수 있는가?
          ├── Yes → Blue-Green (빠른 롤백)
          └── No  → 리스크 감수 수준은?
                    ├── 리스크 최소화 → Canary (점진적 검증)
                    └── 비용 최소화 → Rolling Update (순차 교체)
```

## 5. 정리

| 전략 | 다운타임 | 롤백 속도 | 인프라 비용 | 리스크 | 복잡도 |
|------|---------|----------|-----------|--------|--------|
| Recreate | 있음 | 느림 | 1x | 높음 | 매우 낮음 |
| Rolling Update | 없음 | 느림 | 1.x | 중간 | 낮음 |
| Blue-Green | 없음 | 즉시 | 2x | 낮음 | 중간 |
| Canary | 없음 | 빠름 | 1.x | 매우 낮음 | 높음 |
| A/B Testing | 없음 | 빠름 | 1.x+ | 낮음 | 높음 |
| Shadow | 없음 | N/A | 2x | 없음 | 매우 높음 |

### 핵심 원칙

1. **가장 단순한 전략부터 시작** — 처음부터 Canary를 구현할 필요 없음
2. **롤백 능력이 핵심** — 배포보다 롤백이 더 중요
3. **모니터링은 필수** — 배포 전략은 모니터링 없이는 무의미
4. **데이터베이스 호환성** — 모든 전략에서 DB 마이그레이션이 가장 어려운 부분
5. **점진적 발전** — Recreate → Rolling → Blue-Green → Canary 순으로 성숙
